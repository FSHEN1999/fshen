# mockapi 完整流程记录

## 1. 汇报摘要

本项目的目标，是把原本以 `mock_sit.py` 为核心的 DPU mock 能力，整理成一个可通过 Web API 和前端页面直接操作的小项目，形成“需求可追踪、过程可记录、结果可验证、能力可复用”的闭环。

从管理视角看，这个项目的价值主要有三点：

1. 统一入口，减少 CLI 脚本式操作带来的沟通成本。
2. 结果可视化，便于领导和相关方快速看懂当前进度、风险和产出。
3. 便于后续扩展到 MeterSphere、联调环境和更多 DPU 场景。

## 2. 需求说明

### 2.1 需求背景

- 现有 `mock_sit.py` 已具备完整业务模拟能力，但更偏脚本式使用。
- 需要一个更适合展示和联调的 mockapi 小项目。
- 需要一份可直接给领导看的过程记录，覆盖需求、步骤、AI 参与、产出和耗时。

### 2.2 交付目标

- 保留 `mock_sit` 的业务能力。
- 在 `mockapi/web` 中提供统一 API。
- 在 `mockapi/frontend` 中提供可操作界面。
- 输出一份结构化过程记录，便于复盘与汇报。

## 3. 执行流程

### 3.1 需求确认

- 定位 mockapi 项目目录，确认已有 Web 入口、路由、适配器和前端结构。
- 对照现有 `mock_sit.py`，确认哪些能力已经进入 Web 层，哪些还存在偏差。
- 明确本次优化原则：不推翻业务内核，只做最小而可靠的 Web 适配。

### 3.2 关键判断

- `mockapi/web/app.py` 适合作为统一入口。
- `mockapi/web/services/mock_adapter.py` 负责把 CLI 风格调用转成 API 风格调用。
- `mockapi/web/routes/*` 负责对外暴露稳定接口。
- `mockapi/frontend/src/App.vue` 负责把能力展示给使用者。

### 3.3 实施动作

- 同步 `mockapi/mock_sit.py`，让 Web 小项目与当前业务逻辑保持一致。
- 补齐审批拒绝原因、退回原因和枚举输出。
- 将注册流程的货币选择、offerId 创建和 redirect 行为对齐到最新脚本。
- 在前端增加审批拒绝原因下拉项，并同步注册表单能力。
- 构建前端静态产物，并由 FastAPI 统一托管。

### 3.4 验证动作

- Python 语法检查。
- 前端生产构建。
- FastAPI 健康检查与枚举接口检查。
- 本地服务启动验证。

## 5. 产出结果

### 5.1 代码产出

- `mockapi/mock_sit.py`
- `mockapi/web/models/requests.py`
- `mockapi/web/models/responses.py`
- `mockapi/web/routes/mock_routes.py`
- `mockapi/web/routes/system_routes.py`
- `mockapi/web/services/mock_adapter.py`
- `mockapi/frontend/src/App.vue`

### 5.2 运行产出

- 前端静态资源已构建到 `mockapi/web/static/`
- FastAPI 可直接托管静态页面
- `/api/health` 正常返回
- `/api/enums` 已返回货币、审批拒绝原因和退回原因

### 5.3 可见收益

- 使用方式更统一。
- 联调时更容易解释和演示。
- 后续接 MeterSphere 或其他平台时，接口层更清晰。

## 6. 验证结果

- Python `compileall` 通过。
- 前端 `npm run build` 通过。
- `GET /api/health` 返回 `{"status":"ok"}`。
- `GET /api/enums` 返回 `USD / CNY`、`fraud / others` 和完整原因列表。
- 本地服务已启动，可直接访问 `http://127.0.0.1:8000`。

## 7. 对外汇报口径

建议对外汇报时，按下面顺序讲：

1. 先讲目标：把脚本式 mock 能力变成可展示、可联调的 Web 入口。
2. 再讲动作：需求确认、差异分析、最小改造、验证回归。
3. 再讲结果：接口可用、页面可用、服务可托管、验证通过。
4. 最后讲价值：减少手工操作，提升复用性，便于后续平台化。
