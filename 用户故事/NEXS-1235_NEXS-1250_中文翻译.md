### 用户故事描述

作为 Data Processing Unit，我希望更新卖家在首次申请审批前/后登录 Express Finance 时的处理逻辑，以便卖家在申请过程中拥有顺畅的用户旅程。

本用户故事不覆盖多申请场景。

### 核心规则

| 场景 | 首次审批前 | 首次审批后 |
|---|---|---|
| 点击 `Apply now`，无有效 `SP API auth token` | 跳转至 `SP API authorized consent` | 跳转至 `SP API authorized consent` |
| 点击 `Apply now`，有有效 `SP API auth token` | 跳转至 `SP Authorization Success Page` | 跳转至 `SP Authorization Success Page` |
| Company name | 可修改 | 不可修改 |
| Company USCR/USCI | 可修改 | 不可修改 |
| Business Information | 可修改 | 不可修改 |

### 验收标准

#### AC1：首次申请获批前 Abandon 后，用户重新登录旅程

##### AC1.1：用户通过 HXF website 登录

**前置条件**

- Application status 已变更为 `abandon`。
- 用户尚未提交申请。

**当**

- 用户通过 HXF website 重新登录。

**则**

- 系统按照 offline event journey 继续。
- 用户点击 `Apply now`。
- 如果用户有有效的 `SP API auth token`，用户旅程从 `NEXS-733 Create Offer on AMZ` 开始。
- 如果用户没有有效的 `SP API auth token`，用户旅程从 `NEXS-731 SPAPI consent` 开始。
- 用户将前往 Amazon 完成 `3PL` 授权。
- 当 `3PL` 授权成功后，用户进入 `Business Information page`。
- `Business Information` 自动预填，且 `Company USCI/Name` 可修改。
- `Director / Shareholder information` 为空。

##### AC1.2：用户通过 Amazon 登录

**前置条件**

- Application status 已变更为 `abandon`。
- 用户尚未提交申请。

**当**

- 用户通过 Amazon 重新登录。

**则**

- 系统沿用 existing Amazon Journey。
- 用户点击 `Apply now`。
- 如果用户有有效的 `SP API auth token`，用户旅程从 `Business Information` 开始。
- 如果用户没有有效的 `SP API auth token`，用户旅程从 `SPAPI consent` 开始。
- `Business Information` 自动预填，且 `Company USCI/Name` 可修改。
- `Director / Shareholder information` 为空。

#### AC2：首次申请获批后 Abandon，用户重新登录旅程

##### AC2.1：用户通过 HXF website 或其他渠道登录

**前置条件**

**当**

- 用户通过 HXF website 重新登录。

**则**

- 用户点击 `Apply now`。

- 如果用户没有有效的 `SP API auth token`，用户旅程从 `NEXS-731 SPAPI consent` 开始。
- `Business Information` 自动预填，且 `Company USCI/Name` 不可修改。
- `Director / Shareholder information` 为空。

##### AC2.2：用户通过 Amazon 登录

**前置条件**

- Application status 已变更为 `abandon`。

**当**

- 用户通过 Amazon 重新登录。

**则**

## NEXS-1250 - [CNY LoC] 用户重新登录旅程：放弃提额后重新申请

### 基本信息

| 字段 | 内容 |
|---|---|
| JIRA | NEXS-1250 |
| 标题 | [CNY LoC] The User Re-login Journey: Reapplying After Abandoning Limit Increase |
| 状态 | To Do |
| 项目 | Nexus |
| 修复版本 | R1.1 |
| 类型 | Story |
| 优先级 | Major |
| 报告人 | Adrian Chiu |
| 负责人 | Noah Yao |
| Epic | CNY LoC - FundPark & CN Trustee |
| 创建时间 | 2026-03-02 |
| 更新时间 | 2026-04-02 |

### 用户故事描述

作为 Data Processing Unit (DPU)，我希望更新用户在放弃提额申请后再次重新申请时的处理逻辑，以确保用户旅程顺畅。

### 前置条件

- Seller 已经激活额度。
- 更新后的逻辑适用于因 `e-sign` 过期而变更为 `abandon` 的申请。

### 用户重新申请提额的旅程范围

1. T1/T2：先选择 70k，再申请追加额度至 1.5M。
2. T2：已激活 1.5M offer，且 `Underwritten limit > 1.5M`，随后申请超过 1.5M 的 offer。
3. T2：已激活小于 1.5M 的 offer，通过新增店铺提额，新核批额度高于已签署额度但仍小于 1.5M。
4. T2：已激活小于 1.5M 的 offer，通过新增店铺提额，新核批额度大于 1.5M。
5. T3 的所有旅程。

### 验收标准

#### Common Scenario 1：提额申请因 e-sign 过期而 Abandon

**前置条件**

- 用户过去已经申请过追加额度。
- FundPark 已发送用于完成申请的 `e-sign` 签署链接。

**当**

- 用户 3 个月内未完成签署。

**则**

- 用户会在 Mission Center 看到黄色提醒信息，提示 application expired。
- 在再次申请追加额度前，已激活额度会重新分配到现有店铺，参考 `NEXS-1035`。

#### Common Scenario 2：重新申请更高 offer 时启动授信评估

**前置条件**

- 用户在 Abandon 后希望再次申请追加额度。

**当**

- 用户通过 HXF website 重新登录，并尝试激活更高额度。

**则**

- Seller 需要点击 `Start credit assessment`，重新运行 credit check。
- Seller 需要等待额度申请处理，页面展示 `credit assessment in progress`。
- 当结果成功后，页面展示新的 `underwritten limit`。
- 用户需要点击 `Submit now` 按钮开始申请。

#### AC3：T1/T2 - 先选择 70k，再申请追加额度至 1.5M

**前置条件**

- 提额申请因 `e-sign` 过期而变更为 cancel/abandon。

**当**

- 用户点击 `Submit now` 以提升 credit limit。

**则**

- 用户进入 `Business Information page` 和 `Connected parties page`。
- 两个页面的信息均从上一次提交内容自动预填。
- 用户完成两个页面的信息后，返回 landing page。
- 页面展示提醒信息，提示用户等待结果。
- 当结果就绪后，提醒信息变更为要求用户完成 pending `e-sign` 并绑定 PSP，以完全激活额度。

#### AC4：T2 - 已激活 1.5M offer，且 Underwritten limit > 1.5M，再申请超过 1.5M 的 offer

**前置条件**

- 用户的 `underwritten limit` 为 `CNY > 1.5M`。
- 用户已申请更高额度。
- DPU Application status 因 `e-sign` 过期变更为 `abandon`。

**当**

- 用户点击 `Submit now` 重新提交提额申请。

**则**

- 用户会看到所有 additional document 均从上一次提交内容自动预填。
- 用户需要重新 review T3 document，参考 `NEXS-1170`。
- 页面顶部展示黄色提醒，提醒用户确认文件未过期。
- 当 seller 输入所有必填信息并点击 `Next` 后，用户返回 landing page。
- 页面展示提醒信息，提示用户等待结果。
- 当结果就绪后，提醒信息变更为要求用户完成 pending `e-sign`，以完全激活额度。

#### AC5：T2 - 已激活小于 1.5M 的 offer，新增店铺提额后新核批额度大于 1.5M

**前置条件**

- 用户当前 activated limit 小于 1.5M。
- 用户通过绑定多店铺申请将额度提升至大于 1.5M。

**当**

- 申请超过 3 个月未签署。

**则**

- DPU Application status 在多店铺流程中因 `e-sign` 过期变更为 `abandon`。

**当**

- 用户点击 `Submit now` 重新开始申请。

**则**

- 用户会看到所有 additional document 均从上一次提交内容自动预填。
- 用户需要重新 review T3 document，参考 `NEXS-1170`。
- 页面顶部展示黄色提醒，提醒用户确认文件未过期。
- 当 seller 输入所有必填信息并点击 `Next` 后，用户返回 landing page。
- 页面展示提醒信息，提示用户等待结果。
- 当结果就绪后，提醒信息变更为要求用户完成 pending `e-sign`，以完全激活额度。

#### AC6：T2 - 已激活小于 1.5M 的 offer，新增店铺提额后新核批额度高于已签署额度但仍小于 1.5M

**前置条件**

- 用户在提额流程中新增店铺。
- 新的 `underwritten limit` 高于当前 signed limit。
- 新的 `underwritten limit` 仍小于 1.5M。

**当**

- 用户在 Abandon 后再次点击 `Start credit assessment`。

**则**

- 如果结果成功，Mission Center 会提醒用户进行 `e-sign`。
- 不需要更新 Business Information。

#### AC7：T3 申请追加额度

**前置条件**

- 用户在 Tier 3 申请 additional limit，因此需要提供 additional document。
- 用户因 `e-sign` 过期放弃了该申请。

**当**

- 用户点击 `Submit now` 提供 document。

**则**

- 用户沿用 AC4 的旅程。
