## 2. RAG 问题复盘

### 你原来的表达

你说：

> rag是相当于是一个 ai长期知识库 他主要是结合 es 向量库 存放我们的规则片段...

这个说法里有对的部分，但概念不准。

### 正确理解

RAG 不是“知识库本身”，而是一条链路：

```text
用户问题/ASR片段
→ 向量化
→ 从知识库检索相关规则
→ 把规则作为上下文放进 Prompt
→ LLM 基于规则做判断
```

知识库是存储规则和文档的地方；RAG 是“检索 + 增强 + 生成/判断”的过程。

### 面试回答模板

> 我们用 RAG 的原因是，质检规则、话术规范、黑灰产关键词和业务制度都是企业内部知识，而且会频繁变化。大模型本身不知道这些规则，如果直接把 ASR 文本丢给模型判断，容易出现幻觉或者判断依据不稳定。  
> 所以我们把质检规则和话术规范做成知识库。具体做法是先把规则文档拆成 chunk，再做 embedding 向量化，存到 ES 向量库里。质检时，客服和客户的对话会先通过 ASR 转成文本，然后系统根据通话片段去检索相关规则。  
> 我们不是所有内容都直接走 LLM，而是做了三层处理：第一层是硬规则，比如明确敏感词、黑名单词、固定字段，直接规则匹配；第二层是 RAG，用来召回相似话术和业务规则；第三层才是 LLM，用来处理上下文语义判断，比如隐晦承诺、客户情绪风险、流程遗漏等。  
> 这样做主要解决两个问题：第一，让模型判断有依据，减少幻觉；第二，提升质检覆盖率和准确性，降低人工抽检压力。

### 不要这样说

不要说：

> RAG 是 AI 长期知识库。

建议说：

> RAG 是检索增强链路，知识库只是它的数据来源之一。

## 3. 父子 chunk 问题复盘

### 你的亮点

你说到了很重要的一点：

> 子块召回，父块丢给 LLM。

这个是加分项。

### 你需要修正的表达

你原来表达里有几处问题：

- `铭感词` 要说 `敏感词`。
- `父子快` 要说 `父子 chunk`。
- `出现ai环境` 应该是 `出现 AI 幻觉` 或 `上下文缺失导致误判`。
- `MySQL ES 镜像存储` 要讲清楚：MySQL 存原文和元数据，ES 存检索索引。

### 标准回答

> 父子 chunk 的核心思路是：子 chunk 用来提高召回精度，父 chunk 用来保证上下文完整。  
> 比如一套质检规则里面可能包含规则标题、适用场景、敏感词列表、违规示例和处理建议。如果我们只把整套规则作为一个大 chunk，召回时粒度太粗，相关性分数可能不高；但如果只切成很小的普通 chunk，比如只切到一句敏感词说明，召回虽然准，但丢给 LLM 时上下文不完整，模型不知道这条规则的适用场景和判断边界。  
> 所以我们会把完整规则作为父 chunk，把里面具体的敏感词、话术片段、判断条件切成子 chunk。检索时主要用子 chunk 做向量召回，因为它粒度更细，匹配 ASR 对话更准确；真正组装 Prompt 时，会把子 chunk 对应的父 chunk 或父级上下文一起带给 LLM，让模型看到完整规则，而不是只看到零散一句话。  
> 存储上，我们会保留原文、父子关系、规则 ID、版本号、业务类型等元数据。MySQL 更偏规则原文和元数据管理，ES 或向量索引用来做检索。这样即使向量索引需要重建，也能从 MySQL 的原始规则和元数据恢复，不会丢知识库内容。  
> 如果不用父子 chunk，只用普通 chunk，主要问题有两个：第一，chunk 太大时召回不准；第二，chunk 太小时上下文不够，容易导致模型误判或者解释不完整。父子 chunk 就是在召回精度和上下文完整性之间做平衡。

## 4. 相似度阈值和召回评估复盘

### 你原来的回答

你说：

> 相似度阈值我是用本地的ai coding写了一套相似度匹配逻辑...得出0.86这个余弦匹配数据，至于rag召回我不知道是什么东西

这在真实面试里风险很大。你可以承认不是主负责人，但不能说完全不知道。

### 必补概念：什么是召回

RAG 召回就是：

> 从知识库里把和当前 ASR 对话最相关的规则片段检索出来。

召回效果看：

- 应该命中的规则有没有被召回。
- 正确规则排名靠不靠前。
- 无关规则是不是太多。
- 最终有没有降低误判和漏检。

### 标准回答

> 相似度阈值不是拍脑袋定的。我们会先准备一批真实质检样本，比如敏感词、违规承诺、情绪风险、黑灰产话术等，把这些 ASR 文本和对应应该命中的规则做成测试集。  
> 然后跑向量相似度匹配，看不同阈值下的效果。阈值太低会召回很多无关规则，导致 Prompt 噪声变多；阈值太高又可能漏掉一些同义表达或隐晦表达。我们当时结合测试样本，最后把余弦相似度阈值定在大概 0.86 左右。  
> RAG 召回效果主要看几个指标：第一是召回率，也就是应该命中的规则有没有被召回；第二是 topK 命中率，比如正确规则是否出现在 top3 或 top5；第三是误召回率，无关规则召回太多会干扰模型；第四是最终质检结果的误判率和漏检率。  
> 线上如果发现误判，我们不会只看 LLM 输出，而是先回看检索结果：正确规则有没有召回？召回排名靠不靠前？如果没召回，就是 embedding、切分、query 改写或阈值问题；如果召回了但模型判断错，才重点看 Prompt 和模型输出。

### 必背指标

```text
召回率：该找出来的规则有没有找出来
TopK 命中率：正确规则是否在 top3/top5
误召回率：无关规则是否太多
漏检率：真实违规没识别出来
误判率：不是违规却判成违规
```

## 5. 阈值导致漏检怎么优化

### 你当时回答

你说：

> 我不知道

这题要背模板。

### 标准回答

> 如果阈值 0.86 导致漏检，我不会直接简单把阈值调低，而是先分析漏检原因。  
> 首先看 badcase，判断是检索没召回，还是召回了但模型没判出来。  
> 如果是检索没召回，我会从几方面优化：第一，适当降低相似度阈值，比如从 0.86 调到 0.82 或 0.8，但不能盲目降低，因为阈值太低会引入很多无关规则；第二，增大 topK，比如从 top5 调到 top10；第三，做混合检索，不只靠向量相似度，也加关键词、敏感词、规则 ID、同义词词典匹配；第四，优化 query，把 ASR 对话片段做清洗、摘要或改写，减少口语噪声和 ASR 错字影响；第五，优化 chunk，把容易漏召回的规则重新切分，或者增加父子 chunk 的关联。  
> 如果规则已经召回了，但 LLM 没判断出来，那就不是召回问题，而是 Prompt 或输出规则问题。我会强化 Prompt 里的判断标准，让模型必须引用证据片段，并对低置信度结果转人工复核。  
> 所以整体思路是：先定位漏检发生在检索层还是模型判断层，再分别优化阈值、topK、混合检索、query 改写、chunk 策略和 Prompt。

## 6. Agent 概念复盘

### 你的原始回答

你说：

> agent我理解是ai工作流...会带有rag skills mcp等等 调用的精度更高 并且可以指定做某一件事情

方向对，但不够工程化。

### 标准回答

> 我理解的 Agent 不是简单聊天机器人，而是“大模型 + 任务规划 + 工具调用 + 状态管理”的组合。  
> 普通调用 LLM 接口，一般是把用户问题和 Prompt 发给模型，模型直接返回一段文本。它主要解决的是生成和理解问题。  
> Agent 不一样，它可以根据任务目标判断下一步要不要调用工具，比如 RAG 检索知识库、查业务数据、调用内部接口、创建工单、发送消息，甚至通过 MCP 调用外部工具。模型不只是回答，而是参与决策和编排。  
> 但是生产里的 Agent 不能让模型随便执行动作，必须有边界。我们要定义工具 schema、参数校验、权限控制、超时控制、最大调用次数、审计日志和人工确认。尤其是写操作，模型只能建议或发起，真正执行要经过后端规则校验。  
> 所以我理解 Agent 和普通 LLM 调用的区别是：普通 LLM 是一次问答，Agent 是带工具、带状态、可执行多步任务的受控编排系统。

### 必背短版

> 普通 LLM 调用是一次输入一次输出，模型只负责生成文本。Agent 是大模型加工具调用和状态管理，它能根据任务选择 RAG、业务接口、MCP 工具等完成多步任务。但生产里 Agent 必须受控，要有工具白名单、参数校验、权限、超时、调用次数限制和审计日志，不能让模型随便操作系统。

## 7. Agent 工具 schema 与安全控制

### 你当时回答

你说：

> 我不知道

这题是 Agent 岗高频题，必须背。

### 标准回答

> 如果让我设计 Agent 工具调用系统，我会先把工具当成后端接口来治理，而不是让模型自由发挥。  
> 每个工具都要定义清楚 schema，包括工具名称、工具描述、参数字段、字段类型、必填项、枚举范围、默认值和权限级别。比如订单查询工具，需要 `userId`、`orderId`，参数类型必须明确；如果是创建工单工具，还要限制工单类型、内容长度和业务范围。  
> 防止模型乱传参数，第一层是 JSON Schema 或 DTO 校验，模型输出不符合格式就拒绝或让模型修正；第二层是业务校验，比如 orderId 是否属于当前用户；第三层是权限校验，不能因为模型传了 userId 就信任它，必须以后端登录态和权限系统为准。  
> 对危险工具，我会做分级：只读工具可以自动执行，比如知识库查询、订单查询；写操作工具，比如退款、修改资料、创建工单、发通知，必须有二次确认或人工审核；高风险工具不直接开放给 Agent。  
> 另外还要限制最大调用次数、最大执行时间、工具白名单、审计日志和 traceId。每次工具调用都要记录模型为什么调用、传了什么参数、后端实际执行结果是什么，方便出问题时回溯。

## 8. MCP 复盘

### 你的原始回答

你说：

> mcp对于ai来说相当于一种协议 类如ai调用 本地的cli 调用飞书接口 这就是一种mcp...

这个回答例子不错，但概念要更标准。

### 标准回答

> MCP 可以理解为 Model Context Protocol，是一种让大模型或 Agent 以统一方式连接外部工具和上下文的协议。  
> 它本身不是某个具体能力，而是一个标准接口。比如本地 CLI、飞书接口、数据库查询、知识库检索、文件读取，都可以封装成 MCP Server 提供的工具或资源。Agent 通过 MCP Client 发现这些工具，然后按协议调用。  
> 在 Agent 系统里的价值主要是标准化工具接入。以前每接一个工具，都要为不同模型或不同 Agent 单独写适配；有了 MCP 后，可以把工具统一封装，Agent 只需要按标准协议发现工具、读取资源、调用能力。  
> 比如我可以把飞书通知封装成一个 MCP 工具，Agent 判断需要发通知时，就调用 `send_feishu_message`；也可以把本地日志查询封装成工具，让 Agent 排查问题时读取日志。这样 Agent 不只是生成文本，而是能安全地调用外部系统完成任务。

### MCP 三个常见组成

```text
tools：可执行动作，比如发飞书、查订单
resources：可读取上下文，比如文件、日志、知识库
prompts：可复用提示词模板
```

## 9. LLM 超时、失败、格式不稳定

### 你的亮点

你这题答得比较好。你提到了：

- `ai_task` 表。
- 调用记录。
- 失败状态。
- 定时任务兜底重试。
- 重试 5 次。
- 敏感词规则兜底。
- Kafka 错误事件。
- 错误次数达到阈值后邮件报警。

### 需要修正的词

不要说：

> field 状态

要说：

> FAILED 状态

不要说：

> 热操作

建议说：

> 异常事件流 / 错误事件 / 告警事件

### 标准回答

> 如果模型调用超时或失败，我会先从工程链路上做控制。第一，模型调用必须设置超时时间，不能无限阻塞业务线程。第二，我们会有一张 `ai_task` 表记录每次 AI 调用，包括 taskId、模型、Prompt 版本、状态、请求参数、响应结果、耗时、错误码和重试次数。  
> 如果调用失败，会把任务状态标记为 `FAILED` 或 `RETRYING`，然后由定时任务或延迟队列做补偿重试。重试不会连续打满，一般会设置最大次数，比如 5 次，并结合退避间隔。  
> 如果重试 5 次还是失败，就进入兜底逻辑。比如敏感词、黑名单词这类强规则，不依赖大模型，可以直接走规则引擎兜底，保证核心风险不漏掉。  
> 同时失败事件会写入 Kafka 或错误事件流，后续做统计和告警。如果某个模型、某类规则、某个时间段失败次数超过阈值，就触发邮件或飞书告警，提醒人工处理。  
> 如果是模型返回格式不稳定，比如 JSON 解析失败，我会做结构化输出约束和 JSON Schema 校验。解析失败可以让模型按错误原因重试一次，或者切换兜底 Prompt；多次失败后转人工或规则兜底。  
> 所以整体策略是：超时控制、状态记录、重试补偿、规则兜底、异常事件、阈值告警和人工介入。

## 10. AI 质检误判率突然升高怎么排查

### 你当时回答

你说：

> 我不知道

这题非常高频，必须背。

### 标准回答

> 如果线上 AI 质检误判率突然升高，我会先确认是全局问题还是局部问题。  
> 第一步，看监控指标。比如误判率是所有业务都升高，还是某个坐席、某个业务线、某类质检规则升高；是某个时间点之后升高，还是逐步升高。这样可以判断是系统变更导致，还是数据分布变化导致。  
> 第二步，抽取 badcase。把误判样本拉出来，看模型判错的具体原因。比如是 ASR 转写错误、规则没召回、召回了无关规则、Prompt 输出不稳定，还是模型本身理解错。  
> 第三步，检查最近变更。包括 Prompt 版本、规则库版本、embedding 模型、向量索引、LLM 模型版本、阈值、代码发布、ASR 服务是否有变化。误判率突然升高，通常和最近变更强相关。  
> 第四步，拆链路排查。如果 ASR 文本就错了，那是转写质量问题；如果正确规则没被召回，那是 RAG 检索问题，比如 chunk、embedding、topK、阈值、索引更新；如果规则召回正确但模型判断错，那重点看 Prompt、输出格式和模型版本；如果模型结果正确但最终展示错，那可能是后端解析、入库或规则映射问题。  
> 第五步，先止损。比如回滚 Prompt 或规则版本，切回旧模型，降低自动通过比例，把低置信度结果转人工复核。  
> 第六步，修复后做 badcase 回归，把这批误判样本加入评测集，避免下次再犯。

### 六字流程

```text
指标 → badcase → 最近变更 → 分层排查 → 止损 → 回归
```

## 11. 任务状态表怎么设计

这是下次模拟建议继续问你的题。

### 标准回答

> AI 质检系统里我会设计一张任务表，比如 `ai_task` 或 `quality_check_task`，用于记录每条通话质检任务的状态流转。  
> 核心字段包括：`task_id`、`call_id`、`customer_id`、`status`、`current_step`、`retry_count`、`model_name`、`prompt_version`、`error_code`、`error_message`、`created_at`、`updated_at`、`finished_at`。  
> 状态可以设计为：`INIT`、`ASR_PROCESSING`、`ASR_DONE`、`RAG_RETRIEVED`、`LLM_PROCESSING`、`SUCCESS`、`FAILED`、`RETRYING`、`REVIEW_REQUIRED`。  
> 幂等上，每个任务用 `task_id` 或 `call_id + rule_id` 做唯一键。重复回调或重复消费时，先查当前状态。如果已经是 `SUCCESS`，就直接返回；如果是 `PROCESSING`，要判断是否超时；如果是 `FAILED` 且重试次数没超过限制，可以进入重试。  
> 状态流转也要有限制，比如不能从 `INIT` 直接跳到 `SUCCESS`，不能把已经成功的任务覆盖成失败。这样可以避免 MQ 重复消费、ASR 重复回调、LLM 重试导致的数据错乱。
