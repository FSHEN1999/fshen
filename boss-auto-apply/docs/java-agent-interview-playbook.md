# Java Agent 面试作战手册

适用定位：`4年 Java 后端 + AI 应用落地 / RAG / Agent / Spring Cloud / Redis / Kafka / 金融或质检业务`。

### 1.1 一句话定位

我主要是 Java 后端出身，做过金融和中后台系统，最近把 Java 后端能力往 AI 应用工程上延伸，重点做过大模型质检、RAG 检索增强、Agent 工具调用、异步任务和高并发业务链路。我的优势不是只会调模型接口，而是能把大模型能力接进真实业务系统里，处理稳定性、成本、召回率、延迟、数据权限和工程可维护性。

### 1.2 30 秒自我介绍

面试官您好，我叫宾家豪，做 Java 后端大概 4 年，主要技术栈是 Spring Boot、Spring Cloud、MyBatis、Redis、Kafka、MySQL。之前做过金融信贷、中后台流程、异步回调、幂等补偿、规则引擎和数据库性能优化。最近一段时间重点做 AI 应用落地，项目里涉及 ASR 转写、LLM 质检、RAG 知识检索、Prompt 治理、Agent 工具调用和结果评估。我的理解是 AI 项目真正难点不在于调通接口，而在于怎么把大模型能力稳定、可控、低成本地接进业务闭环，所以我比较关注工程链路、数据质量、召回准确率、异常兜底和线上可观测性。

### 1.3 2 分钟项目讲法

我最近做的项目可以理解为一个 AI 质检平台。业务背景是每天会产生大量客服或销售通话，人工抽检成本高、覆盖率低，所以我们把通话音频先通过 ASR 转成文本，再用 LLM 做质检判断，比如是否触达关键话术、是否违规承诺、是否遗漏风险提示。为了避免大模型只靠通用知识胡乱判断，我们引入了 RAG，把公司制度、话术规则、产品说明、质检标准等文档切分向量化，质检时根据通话内容召回相关规则，再把规则和通话片段一起交给模型判断。

工程上我主要关注几块：第一是异步处理链路，音频转写、文本清洗、规则召回、模型调用、结果入库都不是同步接口里硬等，而是拆成任务状态机和消息队列；第二是 RAG 效果，做了文档切分、向量召回、关键词补召回、重排序和阈值过滤，减少召回不准带来的误判；第三是大模型调用稳定性，包括超时、重试、降级、成本控制、日志追踪和失败补偿；第四是结果可解释，每条质检结论要能反查对应规则、证据片段和模型输出，方便业务复核。

如果岗位更偏 Agent，我会补充：在 Agent 这块，我理解它不是“聊天机器人”，而是让模型根据任务规划选择工具。比如给它开放知识检索、订单查询、规则查询、工单创建、消息通知等工具，模型先判断意图，再选择工具调用，最后组织结果。工程上关键是工具 schema 设计、权限控制、参数校验、调用超时、循环限制、审计日志和人工兜底。

## 2. 核心项目拆解

### 2.1 AI 质检平台

**业务问题**

- 人工质检覆盖率低，抽样容易漏风险。
- 规则经常变化，硬编码质检逻辑维护成本高。
- 只靠关键词匹配误报多，无法理解上下文。

**技术方案**

- 音频通过 ASR 转文本，按说话人、时间戳、轮次切分。
- 对质检规则、产品文档、话术规范做向量化，进入向量库。
- 每次质检先召回相关规则，再把规则、通话片段、评分标准传给 LLM。
- LLM 输出结构化结果：是否违规、命中规则、证据片段、置信度、解释。
- 结果进入复核后台，人工可以确认、驳回、标注原因。

**你负责的点**

- Java 后端接口、任务状态流转、结果入库、查询接口。
- RAG 检索流程：切分策略、召回阈值、混合检索、结果过滤。
- 模型调用封装：超时、重试、日志、错误码、成本统计。
- 质检结果可解释：证据片段、规则 ID、模型原始响应、人工复核状态。

**面试官追问时的亮点**

- 不是一次性 Prompt，而是“规则召回 + 结构化输出 + 人工复核 + 反馈优化”。
- 不是同步阻塞调用模型，而是异步任务、状态机、重试补偿。
- 不是只看准确率，还看召回率、误判率、人工复核通过率、平均处理耗时和单次成本。

### 2.2 RAG 知识库

**为什么要 RAG**

大模型本身不知道公司内部规则，也可能编造答案。RAG 的作用是把内部知识作为上下文注入，让模型基于可追溯的资料回答或判断。

**链路讲法**

文档上传后先做解析和清洗，再按标题、段落、语义边界切分 chunk。每个 chunk 生成 embedding，存入向量库，同时保留文档 ID、章节、版本、权限等元数据。查询时先把用户问题或通话片段向量化，做 topK 召回，再结合关键词检索和重排序，过滤低相关内容，最后把高相关片段拼进 Prompt 让模型输出。

**关键参数**

- `chunk_size`：太大噪声多，太小上下文不完整；常见 300-800 中文字。
- `chunk_overlap`：防止语义被切断；常见 50-150 字。
- `topK`：召回太少容易漏，太多 Prompt 变长且干扰模型；常见 5-10。
- `similarity_threshold`：低于阈值不进入上下文；可从 0.65/0.7 起调。
- `rerank_topN`：先召回 20-50，再重排取 5-8。

**怎么评估 RAG**

- 召回率：标准答案所在文档是否被召回。
- 命中位置：正确 chunk 排名是否靠前。
- 答案正确率：模型最终回答是否符合标准答案。
- 幻觉率：没有资料时是否乱答。
- 延迟与成本：检索、重排、模型调用耗时和 token 成本。

### 2.3 Agent 工具调用

**Agent 是什么**

Agent 本质是“大模型 + 任务规划 + 工具调用 + 状态管理”。普通 Chat 是模型直接回答，Agent 是模型可以判断下一步要不要调用工具，比如查订单、查知识库、创建工单、发通知。

**Java 工程落地方式**

- 定义工具：每个工具有名称、描述、参数 schema、权限范围、超时时间。
- 模型决策：根据用户问题和工具描述，让模型选择工具和参数。
- 参数校验：后端用 JSON Schema 或 DTO 校验，不能信任模型输出。
- 工具执行：调用内部服务或数据库，记录 traceId、耗时、结果。
- 结果回填：把工具结果交给模型总结，或直接返回结构化结果。
- 安全控制：敏感操作必须二次确认，高风险工具不允许模型直接执行。

**常见框架**

- LangChain4j：Java 生态友好，适合快速接入 RAG、工具调用、记忆、模型适配。
- Spring AI：和 Spring Boot 集成自然，适合企业 Java 项目统一接入模型、embedding、vector store。
- MCP：把工具能力用统一协议暴露给模型或 Agent，适合跨工具、跨系统扩展。

**面试表达**

我不会让模型直接“想干什么就干什么”。Agent 在生产里必须有边界：工具白名单、参数校验、权限判断、调用次数上限、超时控制、循环终止条件、审计日志和人工确认。否则模型一旦误判，可能产生错误操作。

## 3. 高频面试题与标准回答

### 3.1 Java 基础

**Q1：HashMap 为什么线程不安全？**

A：HashMap 的 put、resize 都没有并发控制。多线程同时 put 可能导致数据覆盖、链表或红黑树结构异常、size 不准确。JDK 1.7 里扩容时还可能形成环形链表，JDK 1.8 改了扩容逻辑但仍然不是线程安全。并发场景应该用 ConcurrentHashMap，或者在外层加锁，但一般优先 ConcurrentHashMap。

**Q2：ConcurrentHashMap 怎么保证线程安全？**

A：JDK 1.8 主要用 CAS + synchronized。put 时如果桶为空，用 CAS 放入；如果桶不为空，对桶头节点加 synchronized，只锁当前桶，降低锁粒度。size 统计用 CounterCell 分段累加，减少并发竞争。读操作大多数不加锁，通过 volatile 保证可见性。

**Q3：volatile 能保证什么？不能保证什么？**

A：volatile 保证可见性和禁止指令重排序，但不保证复合操作原子性。比如 `count++` 包含读取、加一、写回，多线程下仍然会丢失更新。适合状态标记、双重检查锁里的对象引用，但计数要用 AtomicInteger 或锁。

**Q4：synchronized 和 ReentrantLock 区别？**

A：synchronized 是 JVM 内置锁，使用简单，异常自动释放；ReentrantLock 是显式锁，支持可中断锁、超时获取、公平锁、多个 Condition。普通互斥优先 synchronized，复杂等待通知或公平性需求才用 ReentrantLock。

**Q5：ThreadLocal 用在哪里？有什么风险？**

A：常用于存 traceId、用户上下文、租户上下文。风险是线程池线程会复用，如果用完不 remove，可能内存泄漏或上下文串号。所以在 filter/interceptor 的 finally 里清理。

### 3.2 JVM

**Q1：JVM 内存区域有哪些？**

A：线程共享的有堆和方法区，线程私有的有虚拟机栈、本地方法栈、程序计数器。对象主要在堆上，方法元数据、常量、类信息在方法区。栈存局部变量、操作数栈、方法调用帧。

**Q2：如何排查 OOM？**

A：先看 OOM 类型，是 Java heap space、Metaspace 还是 direct buffer。保留 heap dump，用 MAT 或 jvisualvm 看大对象、引用链和 GC roots。再结合 GC 日志看是否频繁 Full GC。常见原因有集合无限增长、缓存无淘汰、ThreadLocal 未清理、大对象一次性加载。

**Q3：Young GC 和 Full GC 区别？**

A：Young GC 回收新生代，频率高、停顿短；Full GC 回收整个堆和方法区，停顿更长。对象通常先在 Eden 分配，经历多次 Young GC 后晋升老年代。老年代空间不足、元空间不足、大对象分配失败等可能触发 Full GC。

**Q4：线上 CPU 飙高怎么查？**

A：先用 top 找到进程，再用 `top -H -p pid` 找高 CPU 线程，线程 ID 转 16 进制后用 `jstack` 定位具体线程栈。看是死循环、频繁 GC、锁竞争还是正则/JSON/加解密等 CPU 密集逻辑。

### 3.3 Spring / Spring Cloud

**Q1：Spring Bean 生命周期？**

A：实例化、属性注入、Aware 回调、BeanPostProcessor 前置处理、初始化方法、BeanPostProcessor 后置处理、放入单例池、销毁。实际项目里常用初始化钩子加载配置、预热缓存，但要避免启动阶段做太慢或不可控的外部调用。

**Q2：Spring 事务为什么会失效？**

A：常见原因：同类内部方法调用绕过代理；方法不是 public；异常被 catch 没抛出；默认只回滚 RuntimeException；数据库引擎不支持事务；异步线程里事务上下文丢失。解决时要理解 Spring 事务基于 AOP 代理。

**Q3：微服务接口超时怎么处理？**

A：设置合理超时，避免无限等待；加重试但要限制次数，并只对幂等接口重试；加熔断降级，保护调用方线程池；核心链路加监控和 traceId；必要时异步化或削峰。

**Q4：接口幂等怎么做？**

A：可以用唯一业务单号、去重表、Redis setNx、数据库唯一索引、状态机约束。支付、回调、投递、消息消费都需要幂等。关键是让重复请求不会产生重复副作用。

### 3.4 MySQL

**Q1：索引为什么能加速查询？**

A：MySQL InnoDB 常用 B+Tree 索引，能把全表扫描变成树搜索。B+Tree 高度低，叶子节点有序并通过链表连接，适合范围查询。聚簇索引叶子节点存整行数据，二级索引叶子节点存主键，需要回表。

**Q2：什么是最左前缀原则？**

A：联合索引按字段顺序建立，比如 `(a,b,c)`，查询必须从 a 开始连续使用索引。`where a=? and b=?` 可以，只有 `b=?` 通常不行。范围查询后的列可能无法继续用于索引过滤。

**Q3：慢 SQL 怎么优化？**

A：先看慢日志和执行计划，关注 type、key、rows、Extra。常见优化是补合适索引、避免函数包裹索引列、减少 select *、拆分页深翻页、优化 join 顺序、避免大事务。最后再考虑表结构、缓存或读写分离。

**Q4：事务隔离级别有哪些？**

A：读未提交、读已提交、可重复读、串行化。MySQL InnoDB 默认可重复读，通过 MVCC 和间隙锁解决大部分幻读问题。实际业务要平衡一致性和并发性能。

### 3.5 Redis

**Q1：缓存穿透、击穿、雪崩区别？**

A：穿透是查不存在的数据，绕过缓存打到 DB；击穿是热点 key 过期，大量请求同时打 DB；雪崩是大量 key 同时过期或 Redis 故障。对应方案是布隆过滤器/空值缓存、互斥锁/逻辑过期、过期时间随机化/多级缓存/降级。

**Q2：Redis 分布式锁怎么做？**

A：用 `SET key value NX PX ttl`，value 用唯一标识，释放时 Lua 脚本校验 value 再删除，避免误删别人的锁。业务耗时可能超过 ttl 时要续期。锁只能保护临界区，不应长时间持有。

**Q3：Redis 和本地缓存怎么取舍？**

A：本地缓存速度快但多实例一致性差，适合低频变化配置或热点只读数据；Redis 集中管理，一致性更好但有网络开销。常见做法是 Caffeine + Redis 两级缓存，更新时通过 MQ 或版本号失效本地缓存。

### 3.6 Kafka / MQ

**Q1：为什么用 MQ？**

A：解耦、削峰、异步化。比如模型质检链路里，上传音频后不应该同步等 ASR 和 LLM 完成，而是投递任务消息，后台消费处理，前端查任务状态。

**Q2：如何保证消息不丢？**

A：生产端开启确认和重试；Broker 配副本和持久化；消费端处理成功后再提交 offset；业务上做幂等和补偿。严格不丢还要考虑本地事务和消息发送一致性，可用 outbox 表或事务消息。

**Q3：如何处理重复消费？**

A：MQ 通常只能做到至少一次投递，所以消费者必须幂等。可以用业务唯一键、消费记录表、状态机或数据库唯一索引防重复。

### 3.7 AI / LLM / RAG / Agent

**Q1：RAG 和微调有什么区别？**

A：RAG 是检索外部知识后作为上下文输入模型，适合知识经常变化、需要可追溯来源的场景；微调是调整模型参数，适合固定风格、固定任务模式或领域能力增强。企业知识问答、规则质检优先 RAG，因为更新知识不需要重新训练。

**Q2：RAG 为什么会回答错？**

A：可能是文档解析差、切分不合理、embedding 不匹配、召回 topK 太少、阈值太低引入噪声、重排序缺失、Prompt 没约束模型只能基于资料回答。排查要看检索结果，不只看最终回答。

**Q3：怎么减少大模型幻觉？**

A：Prompt 明确要求基于资料回答；没有证据就说不知道；输出必须引用证据片段；结构化输出后做字段校验；低置信度转人工；关键结论用规则或二次模型校验。

**Q4：Agent 工具调用怎么防止危险操作？**

A：工具分级，高风险工具必须人工确认；参数 schema 校验；权限基于当前用户而不是模型；限制最大调用次数和最大执行时间；所有工具调用落审计日志；模型只能建议，关键写操作由后端规则确认。

**Q5：Prompt 怎么设计？**

A：通常包含角色、任务目标、输入数据、判断标准、输出格式、边界条件和示例。生产中我更倾向结构化 Prompt，让模型输出 JSON，再做解析和校验。Prompt 也要版本化，方便 A/B 测试和回滚。

**Q6：怎么做 LLM 调用降级？**

A：超时或失败时可以重试、切备用模型、降低上下文长度、使用规则兜底、进入人工队列。非核心场景可以返回稍后处理，核心场景要保证主流程不被模型服务拖死。

**Q7：怎么控制 token 成本？**

A：减少无效上下文、做摘要缓存、检索只取必要 chunk、Prompt 模板精简、对相同输入做结果缓存、按任务选择小模型或大模型、批处理离线任务。

**Q8：MCP 是什么？**

A：MCP 可以理解为给模型接工具的一套标准协议。以前每个系统都要为不同模型适配工具调用，现在可以把工具、资源、Prompt 通过 MCP Server 暴露，客户端或 Agent 用统一方式发现和调用。对企业内部系统来说，MCP 的价值是工具标准化、权限治理和复用。

## 4. 场景题回答模板

### 4.1 让你设计一个 Java AI 客服助手

**回答结构**

1. 接入层：Web/API/IM，做鉴权、限流、会话 ID。
2. 意图识别：普通问答、业务查询、投诉、人工转接。
3. RAG：检索 FAQ、产品文档、规则制度。
4. Agent 工具：查订单、查用户、建工单、发通知。
5. 安全：权限隔离、敏感信息脱敏、高风险操作确认。
6. 质量：回答引用来源、置信度、人工兜底、反馈闭环。
7. 工程：异步任务、缓存、日志、监控、成本统计。

**可直接说**

我会先把它拆成“问答”和“办事”两类能力。问答走 RAG，保证回答基于企业知识库；办事走 Agent 工具调用，但工具必须有权限、参数校验和审计。比如用户问订单状态，模型不能直接查库，而是调用订单查询工具，后端根据用户身份做权限校验后返回结果。对于退款、修改信息这类高风险操作，Agent 只能生成建议或发起确认，不能直接执行。

### 4.2 RAG 效果不好怎么排查

**回答结构**

1. 先看原始文档是否解析正确。
2. 看 chunk 是否切得合理。
3. 看正确答案所在 chunk 是否被召回。
4. 看召回排序是否靠前。
5. 看 Prompt 是否正确约束模型。
6. 建评测集，按问题类型统计召回率和答案正确率。

**可直接说**

我不会只改 Prompt。RAG 出问题要拆开看：检索有没有召回正确资料，召回资料有没有排在前面，模型有没有按资料回答。比如正确 chunk 没被召回，那是 embedding、切分或 query 改写问题；召回了但排很后，那要加 rerank；资料正确但回答错，才重点调 Prompt 或模型。

### 4.3 LLM 接口线上变慢怎么办

**回答结构**

- 指标：P50/P95/P99、超时率、失败率、token 长度、模型供应商耗时。
- 工程：超时、重试、熔断、限流、异步化、队列削峰。
- 成本：缩短 Prompt、缓存、模型分层。
- 兜底：规则返回、人工队列、稍后处理。

**可直接说**

我会先确认慢在哪里，是检索慢、重排慢、模型首 token 慢，还是输出太长。然后给模型调用设置明确超时和熔断，不让它拖垮业务线程。对非实时任务可以异步化，对实时问答可以做模型分层，简单问题走小模型，复杂问题走大模型，超时进入兜底。

## 5. 面试官可能深挖的“真实性问题”

### Q1：你这个 AI 项目到底是不是你做的？

答法：不要泛泛说“我参与了”，要讲你负责的具体模块。

可说：我主要负责后端工程链路，不是模型训练。具体包括任务状态机、模型调用封装、RAG 检索接口、质检结果入库和查询、失败重试补偿、日志追踪。模型效果部分我参与了 Prompt 和召回策略调优，会和业务一起看误判样本。

### Q2：你们用的什么向量库？为什么？

答法：如果真实项目不方便说具体产品，可以说选型考虑。

可说：我们选型主要看 Java 接入成本、元数据过滤、topK 检索性能、运维复杂度和数据规模。如果规模不大，可以先用 PGVector 或 Elasticsearch dense vector 降低运维复杂度；如果规模变大，再考虑 Milvus 这类专门向量库。

### Q3：你怎么证明 AI 质检准确？

答法：强调评测集和人工复核。

可说：我们不会只看模型自评，而是抽样构建标注集，统计准确率、召回率、误报率、漏报率。上线初期低置信度结果进入人工复核，复核结果反过来沉淀成 badcase，用来优化规则召回和 Prompt。

### Q4：为什么不用纯规则？

答法：规则适合明确边界，LLM 适合语义判断。

可说：纯规则对关键词有效，但通话里很多表达是同义改写、上下文依赖或者隐晦承诺，规则维护成本高。我的思路不是完全替代规则，而是规则和 LLM 结合：硬性红线用规则兜底，语义判断交给 LLM，但要求引用证据并可复核。

### Q5：Agent 会不会不可控？

答法：承认风险，讲工程约束。

可说：会，所以生产 Agent 必须限制边界。模型只能在工具白名单里选择，参数要后端校验，工具要有权限控制，高风险操作要人工确认，并且限制最大调用轮数、超时和审计日志。我的理解是 Agent 是一个受控编排器，不是让模型直接接管系统。

## 8. 最容易翻车的点

- 不要说“我训练了大模型”，除非确实做过训练或微调。
