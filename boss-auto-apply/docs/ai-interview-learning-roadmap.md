# AI 面试学习路线与项目话术

适用定位：`4年 Java 后端 + AI 应用工程化 + RAG + Agent + Spring Boot/Spring Cloud`。

这份资料优先解决三个问题：

1. 面试前到底按什么顺序学。
2. BM25、HNSW、双向召回、RAG、LangChain4j、Spring AI 怎么讲。
3. 项目中遇到的困难怎么回答得像真实做过。

## 0. 一句话定位

面试时先把自己钉在这个位置：

> 我不是算法训练方向，我的定位是 Java 后端 + AI 应用工程化落地。我的重点是把 ASR、RAG、LLM、Agent 工具调用稳定接进业务系统，解决检索准确、调用稳定、结果可解释、成本可控和线上可观测这些工程问题。

不要说自己训练大模型，也不要把 RAG 说成“AI 长期知识库”。要说：

> RAG 是检索增强链路，知识库只是它的数据来源之一。

## 1. 总学习路线

### 第一阶段：先把项目讲顺

必须能 2 分钟说清：

```text
业务背景
-> 为什么人工质检不够
-> ASR 转文本
-> RAG 召回质检规则
-> LLM 做结构化判断
-> 后端做任务状态、重试、入库、查询、复核
-> 难点是准确、稳定、可解释、可追踪
```

标准讲法：

> 我做的是金融客服场景下的 AI 质检平台。系统先把通话音频通过 ASR 转成文本，再把客服和客户的对话片段拿去检索质检规则、话术规范、敏感词和业务制度。召回到相关规则后，把规则、通话片段和评分标准一起交给 LLM 判断，输出是否违规、命中规则、证据片段、置信度和原因。  
> 我主要负责 Java 后端工程链路，包括任务状态流转、模型调用封装、RAG 检索接口、结果入库查询、失败重试、日志追踪和部分 Prompt/召回策略调优。

### 第二阶段：补 RAG 检索知识

按这个顺序学：

```text
文档解析
-> chunk 切分
-> embedding
-> 向量召回
-> BM25 关键词召回
-> 混合召回/双向召回
-> rerank 重排序

-> 评测集和 badcase
```

面试官问 RAG，先别讲框架，先讲链路。框架只是实现手段。

重点只背能落地的：

- Spring AI / LangChain4j 在项目里怎么用。

## 2. RAG 核心链路

### RAG 是什么

RAG 是 Retrieval-Augmented Generation，意思是先从外部知识库检索相关资料，再把资料作为上下文交给大模型回答或判断。

质检项目里可以这样讲：

> 质检规则、产品制度、话术规范都是企业内部知识，大模型本身不知道。如果直接把 ASR 文本丢给模型，它可能凭通用知识判断，容易幻觉。所以我们先召回相关规则，再让模型基于规则和通话片段做判断。

### RAG 链路

```text
文档上传
-> 解析清洗
-> chunk 切分
-> embedding 向量化
-> 存向量、原文、元数据
-> 查询文本向量化
-> 向量召回 + BM25 关键词召回
-> 合并去重
-> rerank 重排序
-> topN 进入 Prompt
-> LLM 结构化输出
-> 证据、规则 ID、模型响应入库
```

### RAG 评估指标

必背：

```text
召回率：该召回的规则有没有召回
TopK 命中率：正确规则是否在 top3/top5
MRR：正确结果排名是否靠前
误召回率：无关规则是不是太多
答案正确率：最终判断是否正确
幻觉率：没有证据时是否乱答
延迟和成本：检索、重排、模型调用耗时和 token 成本
```

## 3. BM25

### BM25 是什么

BM25 是一种传统关键词检索算法，可以理解为“更聪明的关键词匹配”。它会看 query 里的词在文档里出现的频率，也会考虑这个词是不是有区分度。

面试短答：

> BM25 偏关键词召回，适合精确词、专有名词、规则编号、产品名、敏感词这类场景。它不理解语义，但对明确词命中很稳定。

### BM25 看哪几个因素

不用背公式，背三个点：

```text
词频 TF：词在当前文档里出现越多，相关性越高，但不是无限增加。
逆文档频率 IDF：越少见的词区分度越高，比如规则编号、产品名。
文档长度归一化：避免长文档因为词多而天然占便宜。
```

### BM25 的优点

- 对精确关键词稳定。
- 对规则编号、敏感词、产品名效果好。
- 不依赖 embedding 模型。
- 可解释性强，知道是哪个词命中了。

### BM25 的缺点

- 不理解同义表达。
- 对口语、错别字、ASR 错字不友好。
- 对“隐晦承诺”“情绪风险”这类语义问题不够强。

### 项目里怎么讲

> 在质检项目里，BM25 可以用来做关键词补召回。比如规则编号、产品名称、敏感词、黑名单词、固定话术，这些靠 BM25 很稳定。向量召回更适合同义表达和语义相似，比如客户说法和规则描述不完全一样时。我们会把 BM25 和向量召回结果合并，再做去重和重排序。

## 4. HNSW

### HNSW 是什么

HNSW 是 Hierarchical Navigable Small World，是向量数据库里常见的近似最近邻检索算法。它不是精确暴力扫描所有向量，而是构建多层图结构，让查询可以从高层快速跳到低层附近区域，再找到相似向量。

面试短答：

> HNSW 是向量检索常用索引结构，用多层图加速近似最近邻搜索。它牺牲一点点精确度，换取很大的查询性能提升，适合大规模 embedding 检索。

### 为什么需要 HNSW

如果知识库有几十万、几百万 chunk，每次 query 都和所有向量算余弦相似度，成本太高。HNSW 的价值是减少比较次数。

### HNSW 关键词

```text
ANN：近似最近邻
多层图：上层稀疏、下层稠密
召回率和性能权衡
efSearch：查询时搜索范围，越大越准但越慢
M：图中连接数，影响索引大小和召回效果
```

### 项目里怎么讲

> 我不把 HNSW 当算法岗去展开公式。我在项目里的理解是，向量库要解决的是 topK 相似 chunk 快速召回。如果数据量小，可以直接用 ES dense vector 或 PGVector 降低复杂度；如果向量规模变大，就需要 HNSW 这种 ANN 索引来提升检索性能。调参上主要是在召回率、延迟和内存之间做平衡。

## 5. 双向召回 / 混合召回

### 先纠正概念

面试里更常见的说法是“混合召回”或“多路召回”。你说“双向召回”时，可以解释成：

> 我这里说的双向召回，主要是关键词召回和向量语义召回两路一起做，也可以理解为 hybrid search。

不要硬造概念。

### 为什么要双向召回

单靠向量召回的问题：

- 专有名词可能不准。
- 规则编号、产品名、金额、日期这类精确信息可能被弱化。
- embedding 模型对 ASR 错字、短 query 不稳定。

单靠 BM25 的问题：

- 不理解同义表达。
- 规则写法和客户说法不一致时容易漏。
- 对上下文语义判断弱。

所以要两路召回：

```text
BM25 召回：抓精确词、敏感词、规则编号、产品名。
向量召回：抓语义相似、同义表达、隐晦表达。
合并去重：按 documentId/chunkId 去重。
分数融合：按权重、RRF 或归一化分数融合。
Rerank：再用重排模型或规则做最终排序。
```

### 面试标准回答

> 我们不会只依赖一种召回。BM25 适合精确关键词，比如敏感词、规则编号、产品名；向量召回适合语义相似，比如客户用了同义表达或隐晦表达。实际链路里可以先做两路召回，分别取 topK，然后按 chunkId 去重，再用分数融合或 RRF 排序，最后 rerank 取前几个进入 Prompt。这样能降低漏召回，也能控制无关内容进入上下文。

### RRF 是什么

RRF 是 Reciprocal Rank Fusion，用排名融合多路召回结果。它不强依赖不同检索器的原始分数可比性，更适合 BM25 分数和向量相似度这种不同体系。

面试短答：

> RRF 是一种按排名融合的方式。不同召回通道的分数尺度不一样，BM25 分数和向量相似度不好直接相加，所以可以按排名做融合，排名越靠前贡献越大。

## 6. Rerank 重排序

### 为什么需要 rerank

第一阶段召回一般追求“别漏”，所以 topK 会稍宽，比如每路召回 20-50 条。但这些结果里会有噪声，需要第二阶段重排序。

标准回答：

> 召回阶段更看重召回率，宁愿多捞一点；rerank 阶段更看重精度，把最相关的内容排到前面。最后进入 Prompt 的通常只有 5-8 个 chunk，否则 token 成本高，还会干扰模型。

### 项目里怎么讲

> 质检场景更怕漏掉关键规则，所以第一阶段会稍微放宽召回，再通过阈值、元数据过滤和 rerank 控制噪声。如果正确规则没召回，是召回问题；如果召回了但排很后，是排序问题；如果规则在前面但模型还判错，才看 Prompt 和模型。

## 7. LangChain4j

### LangChain4j 是什么

LangChain4j 是 Java 生态里的 LLM 应用开发框架，提供模型调用、Prompt、AI Service、Chat Memory、RAG、EmbeddingStore、工具调用等能力。

面试短答：

> LangChain4j 更像 Java 版的大模型应用编排框架，适合快速做 AI Service、RAG 和工具调用。它的价值是把模型、检索、记忆、工具这些能力抽象出来，让 Java 项目不用从零封装所有细节。

### 面试要知道的核心概念

```text
ChatModel：聊天模型抽象。
EmbeddingModel：文本向量化模型。
EmbeddingStore：向量存储。
ContentRetriever：RAG 内容检索器。
AiServices / @AiService：把接口声明成 AI 服务。
ChatMemory：会话记忆。
Tools：让模型调用 Java 方法或外部工具。
```

### 怎么结合 Spring Boot

> 在 Spring Boot 项目里，可以把 ChatModel、EmbeddingModel、EmbeddingStore、ContentRetriever 注册成 Bean，再定义 AI Service 接口。业务层调用 AI Service，就像调用普通 service 一样。生产里还要在外层加超时、重试、日志、traceId、Prompt 版本和成本统计。

### 面试防守

如果没在线上深用过，不要硬说精通。可以说：

> 我对 LangChain4j 的理解主要在工程接入层，知道它能简化 RAG、AI Service 和工具调用。但生产里我不会完全依赖框架黑盒，关键链路比如检索结果、模型请求、输出解析、异常重试和日志都要自己可控。

## 8. Spring AI

### Spring AI 是什么

Spring AI 是 Spring 生态里的 AI 应用抽象，目标是用 Spring 熟悉的方式接入模型、embedding、vector store、工具调用和 RAG。

面试短答：

> Spring AI 更适合已有 Spring Boot 企业项目。它提供 ChatClient、模型抽象、VectorStore、Advisor、Tool/Function Calling 等能力，让模型调用可以按 Spring Bean 和配置方式管理。

### 面试要知道的核心概念

```text
ChatClient：高层模型调用客户端。
ChatModel：底层聊天模型抽象。
EmbeddingModel：向量化模型。
VectorStore：向量库抽象。
Advisor：类似拦截器/增强器，可用于记忆、RAG 上下文、日志等。
Tool / Function Calling：把 Java 方法或 Bean 暴露给模型调用。
```

### Spring AI 怎么用于 RAG

可以这样讲：

> 文档先切分并通过 EmbeddingModel 向量化，存进 VectorStore。用户问题进来后，先从 VectorStore 检索相关 chunk，再通过 Advisor 或业务代码把检索结果拼进 Prompt，最后用 ChatClient 调模型生成答案。生产里会在这个流程外加权限过滤、topK、阈值、rerank、引用来源和日志。

### Spring AI 和 LangChain4j 怎么选

面试回答：

> 如果项目已经是 Spring Boot/Spring Cloud，Spring AI 集成会更自然，Bean、配置、监控和企业工程习惯更统一。LangChain4j 的 AI Service、RAG、工具调用抽象也很成熟，适合 Java 生态快速搭 AI 应用。实际选型我会看团队熟悉度、模型和向量库支持、是否需要复杂 Agent 编排、可观测性和生产可控程度。

不要争谁绝对更好。说“看场景”。

## 9. 项目困难怎么讲

### 难点 1：RAG 召回不准

标准回答：

> 这个项目里一个难点是 RAG 召回不准。因为 ASR 文本是口语化的，里面有停顿、重复、错字，而质检规则是比较正式的制度文本，两边表达不一致。单靠向量召回可能漏掉规则编号、敏感词；单靠关键词又抓不到隐晦表达。  
> 我们的处理思路是先拆 badcase，看正确规则有没有被召回。如果没召回，就优化 chunk、降低阈值、增大 topK、加 BM25 关键词补召回和同义词；如果召回了但排名靠后，就加 rerank；如果规则已经召回但模型没判对，就改 Prompt 和结构化输出要求。

一句话：

> 先判断是没召回、排序差，还是模型判断错。

### 难点 2：ASR 错字影响质检

标准回答：

> ASR 错字会影响关键词和向量召回。比如产品名、敏感词、金额、时间说错或转写错，检索就可能偏。我们会做文本清洗、业务热词、同义词和规则词典，也会避免只靠单个关键词判断。对低置信度 ASR 或关键风险项，会进入人工复核。

### 难点 3：LLM 输出不稳定

标准回答：

> 模型有时会输出不合法 JSON，或者字段名不稳定。生产里不能直接相信自然语言输出，所以我们要求结构化 JSON，字段包括 rule_id、hit、evidence、confidence、reason。后端会做 JSON Schema 或 DTO 校验，解析失败可以重试一次或切兜底 Prompt，多次失败转人工或规则兜底。

### 难点 4：模型调用超时和失败

标准回答：

> LLM 调用必须设置超时，不能拖垮业务线程。我们会记录 ai_task，包括 taskId、模型名、Prompt 版本、状态、耗时、错误码、重试次数。失败后进入 RETRYING，由定时任务或延迟队列补偿，超过最大重试次数后进入 FAILED 或 REVIEW_REQUIRED。敏感词这类强规则可以走规则兜底。

### 难点 5：质检结论要可解释

标准回答：

> AI 质检不能只给一个“违规/不违规”，否则业务不信，也没法复核。我们会保存命中的规则 ID、规则版本、证据片段、模型原始响应、置信度、Prompt 版本和人工复核结果。这样误判时可以回看是规则没召回、模型误判，还是后端解析入库问题。

### 难点 6：误判率突然升高

标准回答：

> 我会先看是全局升高还是某类规则、某个业务线升高；然后抽 badcase，看是 ASR、召回、rerank、Prompt、模型版本还是后端解析问题；再检查最近变更，比如规则库、Prompt、embedding、阈值、模型版本、代码发布。先止损，比如回滚 Prompt 或规则版本、切旧模型、低置信度转人工；修复后把 badcase 加入评测集回归。

记忆：

```text
指标 -> badcase -> 最近变更 -> 分层排查 -> 止损 -> 回归
```

## 10. 面试高频问答

### Q1：BM25 和向量召回区别？

> BM25 是关键词召回，适合精确词、专有名词、规则编号、敏感词，稳定且可解释，但不理解语义。向量召回是语义召回，适合同义表达和上下文相似，但对专有名词、短 query、ASR 错字可能不稳定。生产里通常做混合召回，再合并去重和 rerank。

### Q2：为什么不用纯向量召回？

> 纯向量召回可能漏掉精确信息，比如规则编号、产品名、敏感词、金额。质检场景里这些词很关键，所以会加 BM25 或规则匹配补召回。

### Q3：为什么不用纯 BM25？

> 纯 BM25 不理解同义表达。客服和客户说话很口语化，不一定和规则文本用同样的词。比如违规承诺可能有很多隐晦说法，这时向量召回和 LLM 语义判断更有价值。

### Q4：HNSW 为什么是近似，不做精确？

> 精确搜索要和所有向量计算相似度，数据量大时延迟和成本高。HNSW 用多层图做近似最近邻，牺牲少量精度换查询性能。实际工程里会通过 efSearch、topK 和 rerank 把召回率拉回来。

### Q5：topK 怎么选？

> topK 太小容易漏召回，太大噪声多、token 成本高。一般第一阶段召回可以取 20-50，rerank 后取 5-8 个进入 Prompt。最终靠评测集调，不是拍脑袋。

### Q6：相似度阈值怎么定？

> 先准备标注集，看不同阈值下召回率、误召回率、topK 命中率和最终误判率。阈值太高漏召回，太低噪声多。我们之前会结合 badcase 和测试样本调，比如从 0.86 往下试 0.82、0.8，但不会盲目调低。

### Q7：RAG 正确规则召回了，但模型还是误判怎么办？

> 这时重点不是召回，而是 Prompt、输出格式和模型判断。可以强化判断标准，要求模型引用证据片段，输出结构化 JSON；对低置信度转人工；也可以加入 few-shot 示例或二次校验。关键是先确认正确规则已经在上下文里。

### Q8：LangChain4j 和 Spring AI 你熟吗？

> 我熟悉它们解决的问题。LangChain4j 更偏 Java LLM 应用编排，AI Service、RAG、工具调用比较方便；Spring AI 更贴 Spring Boot，ChatClient、VectorStore、Advisor、Tool Calling 这些抽象适合企业项目。真正落地时我会把模型调用封装成业务 service，并补上超时、重试、日志、Prompt 版本和成本统计，而不是只依赖框架默认能力。

### Q9：Agent 工具调用怎么保证安全？

> 工具必须白名单化，每个工具有名称、描述、参数 schema、权限级别和超时时间。模型传参后，后端要做 DTO/JSON Schema 校验、业务校验和权限校验。只读工具可以自动执行，写操作要二次确认或人工审核。还要限制最大调用次数、最大耗时，并记录审计日志。

### Q10：怎么证明你不是只会调 API？

> 我会从工程闭环讲：任务状态机、MQ 异步、幂等、补偿、RAG 检索、混合召回、Prompt 版本、结构化输出、人工复核、日志追踪、成本统计和降级。调 API 只是其中一步，真正上线要解决稳定性、可解释性和业务闭环。

## 12. 最后背诵版

你最后至少要背熟这一段：

> 我做 AI 应用落地时，不会只看模型回答，而是把链路拆开。输入侧有 ASR 文本和业务元数据；知识侧有规则文档、chunk、embedding 和向量库；检索侧会做 BM25 关键词召回和向量语义召回，再合并去重、rerank；模型侧要求结构化 JSON 输出；工程侧有任务状态、重试补偿、日志 trace、成本统计和人工复核。  
> 如果效果不好，我会先看正确规则有没有召回；没召回就调 chunk、topK、阈值、BM25 和 query 改写；召回了但排名靠后就看 rerank；规则在上下文里但模型判错，才去改 Prompt、模型和输出约束。这个思路比单纯“调大模型接口”更工程化。
