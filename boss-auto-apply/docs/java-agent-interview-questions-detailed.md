# Java Agent 面试题库与回答话术

适用面试定位：`4年 Java 后端 + AI 应用落地 + RAG + Agent 工具调用 + Spring Cloud/Redis/Kafka/MySQL`。

使用方法：

1. 先背 `一、自我介绍与项目总览`，这是所有面试的入口。
2. 再背 `二、Java 后端基础`，防止面试官觉得你只是蹭 AI。
3. 然后重点背 `三、RAG`、`四、Agent`、`五、AI 工程化`。
4. 每道题都按 `短答 -> 展开 -> 结合项目 -> 追问防守` 来讲。

## 一、自我介绍与项目总览

### Q1：你先做个自我介绍。

**短答：**

面试官您好，我叫宾家豪，做 Java 后端大概 4 年，主要技术栈是 Spring Boot、Spring Cloud、MyBatis、Redis、Kafka、MySQL。之前做过金融信贷、中后台流程、异步回调、幂等补偿、规则引擎和数据库性能优化。最近重点做 AI 应用落地，项目里涉及 ASR 转写、LLM 质检、RAG 知识检索、Prompt 治理、Agent 工具调用和结果评估。我比较关注的不是简单调模型接口，而是怎么把大模型能力稳定、可控、低成本地接进业务闭环。

**展开讲法：**

我的优势主要有三块：第一是 Java 后端工程基础，能处理接口、异步任务、数据一致性、缓存、MQ、数据库优化；第二是业务系统经验，做过金融和中后台流程，对幂等、补偿、审计、状态机比较敏感；第三是 AI 应用工程能力，能把 RAG、Agent、模型调用、评测和降级做成可上线的系统。

**面试官可能追问：你 AI 这块到底做了什么？**

我不是做模型训练，主要做 AI 应用工程。比如把通话文本、质检规则、知识库和大模型串起来，形成自动质检链路；同时负责模型调用封装、RAG 检索、结果结构化、失败重试、人工复核和日志追踪。

### Q2：讲一下你最核心的 AI 项目。

**短答：**

我做过一个 AI 质检平台。业务背景是每天有大量通话，人工质检覆盖率低，所以我们用 ASR 把音频转文本，再结合 RAG 召回质检规则，最后用 LLM 判断是否违规、是否遗漏关键话术，并输出证据片段和结构化结果。

**项目结构：**

- 输入层：音频、通话文本、业务元数据。
- 预处理：ASR、说话人分离、文本清洗、轮次切分。
- 知识层：质检规则、产品说明、话术规范、制度文档。
- RAG 层：文档切分、embedding、向量召回、关键词补召回、重排序。
- 模型层：LLM 质检、结构化 JSON 输出、置信度和解释。
- 工程层：异步任务、MQ、重试补偿、状态机、日志、成本统计。
- 复核层：人工确认、误判标注、badcase 沉淀。

**你负责的点：**

我主要负责后端工程链路，包括任务状态流转、模型调用封装、RAG 检索接口、结果入库查询、失败重试补偿、日志追踪和部分 Prompt/召回策略调优。

**追问防守：你们准确率怎么保证？**

不是只靠模型自评。我们会抽样构建标注集，看准确率、召回率、误报率、漏报率；低置信度结果进入人工复核，复核结果再沉淀成 badcase，用来优化规则召回、Prompt 和阈值。

### Q3：你这个项目的难点是什么？

**短答：**

难点不在于调通 LLM，而在于检索准确、输出稳定、可解释、成本可控和线上可观测。

**三个可讲难点：**

1. RAG 召回不准：文档切分不合理、embedding 不匹配、topK 太小或太大都会影响结果。
2. LLM 输出不稳定：同样输入可能输出格式不一致，所以要结构化输出、JSON 校验、失败重试和兜底。
3. 业务可解释：质检结论必须能反查命中的规则、通话证据片段、模型原始输出和人工复核记录。

**面试表达：**

我理解 AI 项目上线后最怕的是“看起来能回答，但不知道为什么这么答”。所以我们会把结论、证据、规则 ID、置信度和模型响应都存下来，便于复核和追责。

## 二、Java 后端基础高频题

### Q1：HashMap 为什么线程不安全？

**短答：**

HashMap 的 put、resize 没有并发控制，多线程同时写可能导致数据覆盖、size 不准、结构异常。JDK 1.7 扩容时甚至可能链表成环，JDK 1.8 改了扩容方式但仍然不是线程安全。

**追问：那 ConcurrentHashMap 怎么保证线程安全？**

JDK 1.8 主要是 CAS + synchronized。桶为空时用 CAS 放节点，桶不为空时锁桶头节点，只锁当前桶，降低锁粒度。读操作大部分不加锁，通过 volatile 保证可见性。计数用 CounterCell 分散竞争。

### Q2：volatile 能保证什么？不能保证什么？

**短答：**

volatile 保证可见性和禁止指令重排，不保证复合操作原子性。

**例子：**

`count++` 不是原子操作，它包含读、加、写，多线程下会丢更新。要用 AtomicInteger、LongAdder 或锁。

**结合项目：**

如果只是控制任务是否停止，可以用 volatile boolean；如果是统计任务处理数，不能只用 volatile int。

### Q3：线程池核心参数怎么理解？

**短答：**

核心参数包括 corePoolSize、maximumPoolSize、keepAliveTime、workQueue、threadFactory、rejectedExecutionHandler。任务进来后先用核心线程，核心满了进队列，队列满了再扩到最大线程，最大也满了走拒绝策略。

**结合 AI 项目：**

模型调用和 ASR 都是外部 IO，不能无限开线程，否则会打爆供应商接口或拖垮自己服务。我会按下游 QPS、平均耗时和业务峰值来估线程池，并加队列长度、超时、熔断和监控。

**追问：拒绝策略怎么选？**

核心任务不能静默丢弃。通常会记录失败任务，写入补偿表或 MQ 延迟重试。非核心任务可以降级或丢弃，但必须有日志。

### Q4：Spring 事务为什么会失效？

**短答：**

常见原因有：同类内部方法调用绕过代理、方法不是 public、异常被 catch 没抛出、默认只回滚 RuntimeException、异步线程里事务上下文丢失、数据库引擎不支持事务。

**结合项目：**

比如模型任务状态从 `PROCESSING` 更新到 `SUCCESS`，如果中间结果入库失败但异常被吞，事务就不会回滚，会导致状态和结果不一致。所以状态流转和结果写入要么在同一事务里，要么设计补偿机制。

### Q5：接口幂等怎么做？

**短答：**

幂等就是同一个请求重复执行不会产生重复副作用。常用方案有业务唯一键、去重表、Redis setNx、数据库唯一索引、状态机约束。

**结合项目：**

ASR 回调、LLM 任务重试、MQ 消费都可能重复，所以我会用任务 ID + 阶段状态控制。例如同一个 `taskId` 已经是 `SUCCESS`，重复回调就直接返回，不再重复写结果。

### Q6：慢 SQL 怎么排查？

**短答：**

先看慢日志，再看执行计划，重点看 type、key、rows、Extra。常见优化包括加合适索引、避免函数包裹索引列、减少回表、避免深分页、拆大 SQL、控制大事务。

**结合项目：**

质检结果查询一般会按时间、商户、状态、规则类型筛选，所以索引要围绕查询条件设计，而不是盲目给所有字段加索引。

### Q7：Redis 缓存穿透、击穿、雪崩是什么？

**短答：**

穿透是查不存在的数据，缓存没有，打到 DB；击穿是热点 key 过期，大量请求瞬间打 DB；雪崩是大量 key 同时过期或 Redis 故障。

**解决：**

- 穿透：空值缓存、布隆过滤器、参数校验。
- 击穿：互斥锁、逻辑过期、热点永不过期。
- 雪崩：过期时间随机化、多级缓存、限流降级。

### Q8：MQ 如何保证消息不丢？

**短答：**

生产端确认和重试，Broker 持久化和副本，消费端处理成功后再提交 offset，业务侧做幂等和补偿。

**结合项目：**

AI 质检任务可以用 MQ 解耦，上传音频后只创建任务并投递消息，消费者异步处理 ASR、RAG、LLM。即使消费失败，也能根据任务表状态补偿。

## 三、RAG 面试题

### Q1：RAG 是什么？为什么不用直接问大模型？

**短答：**

RAG 是 Retrieval-Augmented Generation，先从外部知识库检索相关资料，再把资料作为上下文交给大模型生成答案。直接问大模型会缺少企业内部知识，也容易幻觉。

**结合项目：**

质检规则、产品说明、话术规范是公司内部知识，大模型本身不知道，所以要先召回相关规则，再让模型基于规则和通话片段判断。

### Q2：RAG 链路怎么设计？

**标准回答：**

1. 文档接入：上传、解析、清洗。
2. 文档切分：按标题、段落、语义边界切 chunk。
3. 向量化：每个 chunk 生成 embedding。
4. 存储：向量、原文、文档 ID、章节、版本、权限元数据。
5. 查询：query embedding 后 topK 召回。
6. 混合检索：向量召回 + 关键词召回。
7. 重排序：rerank 过滤噪声。
8. Prompt 拼接：资料 + 问题 + 输出格式。
9. 模型输出：结构化答案。
10. 评测：召回率、正确率、幻觉率、延迟、成本。

### Q3：chunk_size 和 overlap 怎么选？

**短答：**

chunk 太大噪声多，太小语义不完整。中文常见 300-800 字，overlap 50-150 字。最终要靠评测集调参。

**追问：为什么要 overlap？**

防止重要语义刚好被切断。比如一条质检规则的条件在上一段，处罚标准在下一段，如果没有 overlap，检索到的 chunk 可能上下文不完整。

### Q4：topK 怎么选？

**短答：**

topK 太小容易漏召回，太大上下文噪声多、token 成本高、模型容易被干扰。一般先召回 20-50，再 rerank 取 5-8 个进入 Prompt。

**结合项目：**

质检场景更怕漏掉关键违规规则，所以第一阶段召回可以稍宽，后面靠 rerank 和阈值过滤控制噪声。

### Q5：RAG 回答错了怎么排查？

**必背回答：**

我不会一上来就改 Prompt，而是拆链路排查：

1. 原始文档解析是否正确。
2. chunk 是否切得合理。
3. 正确答案所在 chunk 是否被召回。
4. 正确 chunk 排名是否靠前。
5. rerank 是否把正确内容过滤掉。
6. Prompt 是否明确要求基于资料回答。
7. 模型是否输出格式错误或幻觉。

**一句话：**

如果正确资料没召回，是检索问题；召回了但排很后，是排序问题；资料正确但答错，才是 Prompt 或模型问题。

### Q6：怎么评估 RAG 效果？

**短答：**

要建评测集。指标包括召回率、MRR、答案正确率、幻觉率、引用准确率、延迟和成本。

**结合项目：**

质检项目里可以抽取历史通话和人工质检结果作为标注集，看模型是否命中正确规则、是否给出正确证据片段、是否误判或漏判。

### Q7：RAG 和微调有什么区别？

**短答：**

RAG 是把外部知识检索出来作为上下文，不改模型参数；微调是调整模型参数。企业知识经常变、需要可追溯来源时优先 RAG；固定任务风格和领域表达可以考虑微调。

**追问：什么时候微调？**

当任务模式固定、数据量足够、Prompt 成本高、通用模型不稳定时可以微调。但内部制度和规则更新频繁，仍然要配合 RAG。

### Q8：怎么减少 RAG 幻觉？

**回答：**

- Prompt 明确要求只基于资料回答。
- 没有证据就回答不知道。
- 输出必须引用证据片段。
- 结构化 JSON 输出并做字段校验。
- 低置信度转人工复核。
- 对关键结论做规则校验或二次模型校验。

## 四、Agent 面试题

### Q1：你理解的 Agent 是什么？

**短答：**

Agent 不是简单聊天机器人，而是“大模型 + 任务规划 + 工具调用 + 状态管理”。它能根据任务选择工具，比如查知识库、查订单、建工单、发通知，然后综合工具结果给出答案或执行下一步。

**结合项目：**

比如质检平台里，Agent 可以根据任务调用规则查询、通话查询、质检结果查询、工单创建等工具，但工具必须受权限和参数校验约束。

### Q2：Agent 和普通 ChatBot 有什么区别？

**短答：**

普通 ChatBot 主要生成文本；Agent 可以调用工具、读取外部状态、执行多步任务。Agent 的核心难点是工具边界、状态管理、循环控制和安全审计。

### Q3：Agent 工具调用怎么设计？

**回答结构：**

1. 工具名称：清晰表达能力。
2. 工具描述：让模型知道什么时候用。
3. 参数 schema：字段类型、必填、枚举、范围。
4. 权限控制：基于当前用户，不信任模型。
5. 超时和重试：防止工具拖垮链路。
6. 结果格式：返回结构化数据，便于模型总结。
7. 审计日志：记录谁、何时、调用什么工具、参数和结果。

### Q4：Agent 最大风险是什么？

**短答：**

最大风险是模型误判后执行了错误工具，尤其是写操作和敏感操作。

**防守方案：**

- 工具白名单。
- 参数 schema 校验。
- 权限校验在后端做。
- 高风险操作人工确认。
- 最大调用轮数限制。
- 超时控制。
- 全链路审计日志。
- 不允许模型直接拼 SQL 或直接操作数据库。

### Q5：Agent 循环调用停不下来怎么办？

**回答：**

要设置最大步骤数、最大工具调用次数、最大耗时、相同工具重复调用限制。如果多轮后没有新信息，就强制结束并返回“需要人工处理”。同时记录 trace，方便复盘为什么循环。

### Q6：工具调用失败怎么办？

**回答：**

先区分失败类型：参数错误、权限不足、业务不存在、下游超时、系统异常。参数错误可以让模型修正一次；权限不足直接拒绝；下游超时可以重试或降级；系统异常记录日志并提示人工介入。

### Q7：MCP 是什么？和 Agent 有什么关系？

**短答：**

MCP 可以理解为给模型接工具和资源的一套标准协议。它让工具能力以统一方式暴露给 Agent，Agent 可以发现工具、读取资源、调用能力。

**面试表达：**

以前每个模型或客户端都要单独适配工具调用，MCP 的价值是标准化工具接入。对企业内部来说，可以把订单查询、知识库检索、工单系统、消息通知封装成 MCP Server，由不同 Agent 复用。

### Q8：Java 里怎么做 Agent？

**回答：**

可以用 LangChain4j 或 Spring AI。LangChain4j 更偏 Java 生态的 LLM 应用编排，适合 RAG、工具调用、记忆；Spring AI 和 Spring Boot 集成更自然，适合企业项目统一管理模型、embedding、vector store。生产里我会把模型能力封装成 service，而不是让业务代码到处直接调模型 API。

## 五、AI 工程化面试题

### Q1：LLM 接口超时怎么办？

**回答：**

首先要设置明确超时，不能无限等待。然后按业务重要性处理：实时接口可以降级、返回稍后处理或切备用模型；离线任务可以重试、延迟队列、补偿表。还要记录模型、prompt 版本、token 数、耗时、错误码。

### Q2：怎么控制 token 成本？

**回答：**

- 缩短 Prompt 模板。
- RAG 只放高质量 chunk。
- 对重复输入做缓存。
- 简单任务用小模型，复杂任务用大模型。
- 离线批处理合并请求。
- 长文先摘要再判断。
- 记录每次调用的 input/output token 和费用。

### Q3：怎么做 Prompt 管理？

**回答：**

Prompt 要版本化，不能散落在代码里。每个 Prompt 记录版本、适用场景、输入字段、输出格式、变更原因和评测结果。上线前用 badcase 回归，效果不好可以快速回滚。

### Q4：为什么要结构化输出？

**回答：**

生产系统不能只拿一段自然语言当结果。结构化 JSON 方便入库、校验、统计和后续流程处理。比如质检输出要有 `rule_id`、`hit`、`evidence`、`confidence`、`reason`，字段不合法就重试或转人工。

### Q5：大模型结果怎么入库？

**回答：**

我会存四类信息：业务结果、证据片段、模型原始响应、调用元数据。调用元数据包括模型名、Prompt 版本、token 数、耗时、traceId、错误码。这样方便排查、复盘和成本统计。

### Q6：AI 结果错了谁负责？怎么设计系统？

**回答：**

系统要承认模型可能错，所以不能让高风险结果直接生效。要有置信度、证据、人工复核、审计和回滚。模型适合做辅助判断，关键决策要保留规则兜底或人工确认。

## 六、项目深挖题

### Q1：你的项目为什么不用纯关键词规则？

**回答：**

纯规则适合明确表达，比如出现某些禁词就判违规。但通话里很多表达是同义改写、上下文依赖或者隐晦承诺，规则维护成本高。所以我们采用规则和 LLM 结合：硬性红线用规则兜底，语义判断交给 LLM，但必须引用证据并能人工复核。

### Q2：你们怎么处理 ASR 错字？

**回答：**

ASR 错字会影响质检，所以会做文本清洗、热词纠错、业务词典和证据片段复核。对关键规则不能只靠单个关键词，要结合上下文和相似表达。低置信度 ASR 或低置信度质检结果转人工复核。

### Q3：任务状态机怎么设计？

**回答：**

可以设计为 `INIT -> ASR_PROCESSING -> ASR_DONE -> RAG_RETRIEVED -> LLM_PROCESSING -> SUCCESS/FAILED/REVIEW_REQUIRED`。每个阶段记录开始时间、结束时间、错误码和重试次数。状态流转要幂等，防止重复回调或重复消费导致状态错乱。

### Q4：失败重试怎么做？

**回答：**

失败要分类型。网络超时、限流、临时 5xx 可以重试；参数错误、权限错误、数据不存在不应盲目重试。重试要有最大次数和退避策略，超过次数进入失败表或人工处理。

### Q5：怎么做可观测性？

**回答：**

至少要有日志、指标、trace。日志记录 traceId、taskId、模型名、Prompt 版本、耗时、错误码；指标看成功率、失败率、P95 延迟、token 成本、人工复核率；trace 串起 ASR、RAG、LLM、入库整个链路。

### Q6：如何证明你不是只会调 API？

**回答：**

我会讲工程闭环：异步任务、幂等、补偿、RAG 检索、Prompt 版本、结构化输出、人工复核、日志追踪、成本统计和降级策略。调 API 只是其中一步，真正上线要解决稳定性、可解释性和业务闭环。

## 七、系统设计题

### Q1：设计一个企业知识库问答系统。

**回答框架：**

1. 文档接入：支持 PDF、Word、网页、Markdown。
2. 解析清洗：去页眉页脚、表格处理、OCR。
3. 切分向量化：chunk + embedding + 元数据。
4. 权限控制：按用户、部门、文档权限过滤。
5. 检索：向量 + 关键词 + rerank。
6. 生成：基于证据回答，引用来源。
7. 反馈：点赞、点踩、人工纠错。
8. 运维：评测集、监控、成本、版本回滚。

### Q2：设计一个 Agent 客服助手。

**回答框架：**

1. 意图识别：问答、查询、投诉、人工转接。
2. RAG：检索 FAQ、产品文档、规则。
3. 工具：订单查询、工单创建、消息通知。
4. 权限：工具调用基于用户身份。
5. 风控：高风险操作二次确认。
6. 兜底：低置信度转人工。
7. 监控：解决率、转人工率、错误率、成本。

### Q3：设计一个 AI 质检平台。

**回答框架：**

1. 音频上传或通话接入。
2. ASR 转写。
3. 文本清洗和说话人切分。
4. RAG 召回质检规则。
5. LLM 结构化判断。
6. 证据片段和规则 ID 入库。
7. 人工复核和 badcase 回流。
8. 统计报表和风险告警。
